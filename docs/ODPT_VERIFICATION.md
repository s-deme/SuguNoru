# ODPT時刻表の取得・保存・表示の検証

## 原因と修正

2026-09-19、停留所取得後に時刻表取得が失敗する処理を調査した。

1. ODPT取得処理が集計前に空の `OfficialTimetableParser.Timetable` を生成していた。同クラスは空を禁止しているため、便の取得に進む前に例外が発生していた。集計を終えてから結果を生成するよう変更した。
2. 実際の `odpt:calendar` は `odpt.Calendar:Specific.Toei.65-100` などのID。旧処理はIDに `Weekday` 等の文字が含まれる場合しか扱わず、実データの便を捨てていた。[公式Calendar API](https://api-public.odpt.org/api/v4/odpt:Calendar?odpt:operator=odpt.Operator:Toei)の `odpt:day` と `odpt:duration` を取得し、日付と発車時刻を保存するよう変更した。
3. 旧処理は土曜と日曜・休日を同じ配列へ足し、空欄なら他曜日の時刻へ代替していた。ODPT取得結果については日付別データを正とし、未運行日や保存期間外に便を生成しない。名称のない臨時運行カレンダーもIDと日付で扱う。

新規取得、旧方面指定、保存後の更新は同じ取得処理を使う。運行日が不明な便は黙って除外せず、取得失敗として既存データを保持する。APIエラーは路線・停留所・時刻表・運行日のどの取得で失敗したかを区別する。トークンは引き続き端末のプライベート設定に保存し、時刻表・バックアップへ含めない。

## 検証範囲

- Android上で製品と同じ `OdptTimetableFetcher` を使い、公開APIに対して全43系統の代表区間を検証。路線・標柱名・便・カレンダーを取得し、43/43で日付別時刻表の生成とJSON保存復元が成功。
- 各系統で最長経路の最初の乗車可能停留所から、最後の別名称停留所までを選択。全停留所組み合わせを総当たりした検証ではない。
- 対象に平日のみの錦18、急行05・06、直行03、循環・分岐経路を含む。テスト結果は経路数とカレンダー数を系統ごとに出力する。
- 日付別データの保存復元・更新失敗時の保持・複製、公式ページ取得への切り替え、日付選択画面と編集保存、旧形式との互換性を回帰テストで検証する。
- 最終確認では単体テスト42件、Android回帰テスト7件、実APIテスト（43系統）が成功。無効トークンの認証エラー表示も確認した。ライト・ダーク表示を確認し、lintはエラー0件・警告5件。
- 公開APIは `api-public.odpt.org`、製品はトークン付きの `api.odpt.org`。公開APIの成功だけでは個々のトークンの利用権限を証明できない。この作業環境には実トークンがないため、有効トークンによる認証確認は未実施。

## 再実行

JDK 17以上とAndroid SDKを設定し、`./gradlew.bat -I scripts/verification.gradle testDebugUnitTest lintDebug assembleDebug assembleDebugAndroidTest` を実行する。検証用のメインAPKとandroidTest APKをインストールする（パッケージは `jp.sugunoru.app.verification`）。

PowerShell 7で `./scripts/verify-odpt.ps1` を実行すると公開APIで43系統を検証する。認証付き検証は `./scripts/verify-odpt.ps1 -TokenFile <Git管理外のトークンファイルのパス>`。ファイルにはトークン本体だけを保存する。値はコマンド引数やログに出さず、検証アプリのプライベート領域へ標準入力で渡し、終了時にテスト用コピーを削除する。

`OdptLiveTest` は私有設定がない場合にSKIPPEDを出力する。通常の回帰テストが通っただけでは実API検証済みと扱わない。
